# 修正版GUIの実動作確認手順・記録表

作成日: 2026-09-24。[English](live-verification.en.md) / [説明書目次](README.md)

対象は[PR #84](https://github.com/inata169/dicomxphits/pull/84)を含む版の「3 PHITS」観測表示です。これは確認計画と未記入の記録表であり、実計算での合格報告ではありません。今回の承認範囲は文書作成だけです。

## 1. 始める前に

1. 現在の10 threads計算は、そのまま終了を待ちます。この確認のためにSTOP・強制終了・ファイル変更・GUI再起動を行いません。
2. 計算終了はGUIの工程状態とActivity logで確認します。残バッチ数0や小さな相対誤差だけでは完了を判断しません。失敗・中断なら、通常の[説明書](gui-manual.ja.md)の復旧手順で扱います。
3. 終了後、修正を含むコードから起動できることを確認します。mainへのマージは、インストール済みアプリや起動中GUIの更新を意味しません。修正コミットは `95fc06d4d0d9589fd6c2f4f145c616be74807251`、マージは `fa5f0a32d98b8c843cec9bf42f6610d45e92d866`。ローカルの `b45e623` も同じ修正内容です。v1.1.0という表示だけでは識別できません。
4. 起動方法・使用版・使用する非患者ファントム・新規の検証用出力先・maxcas/maxbch/threads・観察期間を事前に決め、記録します。過去の計算フォルダの上書きや、表示確認のための入力改変は行いません。
5. 実PHITSを使う確認の実行条件は別途明示して承認を得ます。この文書を作成しただけでは、新しい計算や再計算は開始しません。教育・研究の固定照射3D-CRTの範囲で実施します。

記録表はリポジトリ外の検証記録用フォルダにコピーしてから記入してください。このフォルダには空欄の雛形だけを保持し、実出力、DICOM、UID、個人情報、実データの画面画像や個別設定を追加しません。ケースやパスは公開用の記録では匿名の識別名を使います。

## 2. 表示の読み方

| 項目 | 判定時の意味 |
| --- | --- |
| `Observed remaining batches` | 現在のセグメントの暫定残数。全ケースの進捗率・完了証拠ではありません。 |
| `prepared total` | 準備時の総バッチ数。同一セグメント中に変えません。 |
| `Isocenter voxel r.err` | 現在のセグメントの単一ボクセルに対する暫定統計相対誤差。Structure評価とは別です。 |
| `provisional` | 条件を満たして採用した観測値。原子的なPHITS結果や収束保証ではありません。 |
| `stale` / `age` | 最後に採用したサンプルが古い状態。新サンプルが5秒ない場合にも表示されます。長いバッチの途中では正常に発生します。 |
| `Unavailable` | 現在の値を安全に提示できない状態。PHITSの失敗を直接意味しません。 |

観測は1秒より速く行われず、完全な内容が連続2回一致して初めて新サンプルを採用します。途中のバッチ番号を飛ばすことや、書換え中に一時的に利用不可になることがあります。GUIの数値は丸められるため、元の値が変わっても同じ表示になる場合があります。**相対誤差の毎回の低下は合格条件にしません。**

## 3. 通常の更新を確認する

1. 承認された検証条件で修正版GUIを起動し、通常の手順で検証用workspaceを準備します。PHITS 3.35 Windows OpenMPの対応構成を使い、`3 PHITS` → `Run PHITS segments`からそのGUIが所有する計算を開始します。完了済みケースを開くだけではライブ観測は開始されません。
2. 最初の有効な観測が出た時刻、現在のセグメント、残数、prepared total、r.err、各行の状態とageを記録します。
3. 30〜60秒程度の間隔、または表示が変わったタイミングで記録します。これは人間の記録間隔で、アプリの観測間隔は変更しません。同一セグメントで、可能なら3つの異なる採用サンプルを記録します。
4. セグメントが変わったら区切りを入れます。新しいセグメントの残数やr.errを前のセグメントと連続した単調変化として比較しません。
5. 事前に決めた観察期間で判定します。必要な更新が発生しなければ「未確認」とし、自動で計算時間・履歴数・再実行回数を増やしません。記録を終えることと計算を停止することは別です。計算は承認された終了方針に従います。

### 確認項目と合格条件

| ID | 確認内容 | 合格条件 / 未確認になる条件 |
| --- | --- | --- |
| A | 残バッチ数の更新 | 同一セグメントで新しく採用された残数の減少を観察し、0〜prepared total内である。各バッチをすべて表示する必要はない。 |
| A1 | 分・秒形式の回帰確認 | 読み取りが承認された場合、現在の完全なbatch記録のCPU時間が分・秒形式であり、その世代以降の残数が採用される。秒形式しか発生しない、または元記録を確認しない場合は、この項目だけ未確認。形式を作るために実ファイルを書き換えない。 |
| B | Isocenter相対誤差の更新 | 完全な新しいペアに対応する採用サンプルへの更新を観察する。値の変化、または採用時刻・ageの更新で区別する。同じ丸め値の継続や一時的な増加だけで不合格にしない。新しいペアが発生しなければ未確認。 |
| C | 一時障害後の復帰 | 下記の区別に従う。実環境で障害がなければ「発生せず・未確認」とし、合成テスト成功で実環境の合格欄を埋めない。 |
| D | セグメント移行・終了 | 前のセグメントの値が新しい値として引き継がれない。終了後にライブ表示が消える/利用不可になるのは正常。終了判定には工程状態・ログを使う。 |

## 4. 一時障害からの復帰

自然に`stale`や一時的な利用不可が出た場合、開始時刻と、その後に新しい観測が採用された時刻を記録します。ただし、`stale → provisional`だけでは「Windows共有競合からの復帰」を証明できません。通常のバッチ更新待ちでも同じ遷移が起こります。

Windows共有・アクセス競合の回帰確認は、実計算フォルダをロック・編集・削除せず、開発用の合成テストで行います。PR #84では次のテストが成功済みです。これは新たな実行指示ではありません。

- `test_publication_recovers_from_sharing_failure_on_new_sample`: Windowsエラー5/32/33後、新しいサンプルで再公開すること。
- `test_windows_sidecar_reader_cannot_permanently_stop_observation`: 合成ファイルで実際のWindows共有競合を発生させ、競合解消後に復帰すること。
- `test_unsafe_publication_still_disables_observer`: 危険な出力先を拒否し続けること。

復帰対象は指定の一時的なWindows競合です。すべての例外から自動復帰する保証ではありません。観測再開を計算の再実行・再開と取り違えないでください。

## 5. 更新が止まったように見えるとき

1. セグメントID、表示値、状態、age、時刻を記録します。確認のために計算を止めたりファイルを修正したりしません。
2. 別途読み取りを許可された場合だけ、検証用workspaceの `analysis/phits_observation.json` を短時間で読み、直ちに閉じます。読み取り自体で置換を長く妨げるアプリは使いません。実ファイルを編集して保存しません。
3. 同じ実行・セグメントで `sequence` が進むか、`batch` / `error` の `reason`、`sample_utc`、`sample_age_seconds` がどう変わるかを比較します。GUI上のageは最終公開後の経過も加算するため、JSON内のageとは一致しないことがあります。
4. sequenceが進んでいてサンプル時刻だけが古い場合は、未更新の元出力や解析拒否を疑います。sequence自体が止まる場合は、観測・公開処理の停止を疑います。どちらも、それだけで原因を確定しません。`reason=available`でも同じ元サンプルのままならageは増えます。
5. `unsupported-format`、`resource-limit`、`pair-mismatch`などの理由は加工せず記録し、調査へ引き継ぎます。出力が変わったという事実だけでは、完全な対応ペアが利用可能だった証明にはなりません。終了時は観測JSONが削除される場合があります。
